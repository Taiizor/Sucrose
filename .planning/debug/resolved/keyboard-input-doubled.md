## Resolution

root_cause: the desktop surface is a cross-thread child of explorer's Progman, so Windows attaches the renderer's input queue to explorer's desktop thread (WebView2's widget thread joins through its parent); Chromium's widget takes the Win32 keyboard focus of that shared state (CEF at navigation, a forwarded click on either engine) and then receives every real keystroke typed while the desktop is in front; AND the renderer posted its raw-input copy of the same key (legacy forwarding) without checking where the real key goes, so the page saw each keydown/keyup twice
fix: 6fb2c103 fix(input): render.rs posts a forwarded key only when input::should_post says so: not while DesktopSurface::has_keyboard_focus() (the foreground window's thread has its keyboard focus on the surface or a descendant, e.g. CEF's Chrome_WidgetWin_1 or WebView2's widget; foreground::keyboard_focus_within via GetForegroundWindow, GetGUIThreadInfo, IsChild), because Windows already delivers the real key to the page then; otherwise the legacy WM_KEYDOWN/WM_KEYUP post as before; mouse unchanged; a debug log line when the page focus state changes (no key content); unsupported.rs stub returns false
oracle_type: specified (one physical key press = one keydown and one keyup in the page, the legacy behavior) for the probe; derived (the legacy message pair, the focus decision) for the unit tests

## Prevention

five_whys:
  - branch: code
    chain: "the page got every key twice -> the renderer posted a key the OS also delivered -> the forwarding was ported from the legacy app, which posted unconditionally -> nothing modelled where the real keystroke goes once a page widget lives inside a shell-owned window tree -> the input path had unit tests for the message translation only, none for the delivery decision"
  - branch: environment
    chain: "Windows delivered the real key to the widget -> the widget held the keyboard focus of the foreground (shell desktop) input state -> a cross-thread child window attaches its thread's input queue to the parent's thread (Progman), and the Chromium widget threads join it -> CEF focuses the browser at navigation (no CefFocusHandler), a forwarded click focuses either engine -> the attachment is implicit Win32 behavior that no code or doc named"
  and_gate: "yes: shared input state with the widget focused AND the desktop being the foreground AND the unconditional post; the fix removes the post exactly when the first two hold"
why_not_caught: "no gate existed for this class: the unit tests covered the translation of one raw record into one message, not whether the page also gets the real key; real keystrokes can only come from the maintainer (synthetic input is not allowed) and the real-keyboard check of plan 04-20 had not been done yet; the legacy app's identical post was taken as the reference"
recurrence_guard: "crates/sucrose-platform/src/input.rs tests a_key_is_left_to_windows_while_the_page_has_the_keyboard_focus_itself (the focus decision, killed by the post-every-key mutant), one_key_press_posts_exactly_one_keydown_and_one_keyup (one legacy pair, no WM_CHAR, no second keydown) and mouse_events_are_always_posted_and_never_look_up_the_keyboard_focus; crates/sucrose-platform/src/os_windows/foreground.rs test a_window_is_within_itself_and_its_ancestors_but_not_its_children_or_strangers; the docs/ARCHITECTURE.md renderer row names the shared input state; KB pattern: a window embedded under a shell window shares the shell thread's input state, so before posting any input to an embedded widget check where the OS already routes the real input (keyboard focus for keys; hit test and capture for the mouse)"
