## Phase Goal

ROADMAP goal: *An existing user's selected video theme plays behind the desktop icons on every monitor on Windows through libmpv, survives shell and monitor changes, and pauses for fullscreen apps.*

This plan's slice (UAT gap G-02-2b, and the root cause of G-02-6, wiring half): **the video plays smoothly on a hybrid-GPU laptop because Sucrose asks Windows for the high-performance GPU, exactly as the C# app does.** Plan 02-17 built the platform side (`GpuPreference`, `Platform::set_gpu_preference`, `Platform::gpu_adapters`, `Platform::default_gpu_adapter`, the `gpu_preference` capability); this plan reads the setting, applies it before the renderers start, logs each renderer's adapter and records DESK-12 as shipped. The maintainer decided in UAT (test 6, option 1) to pull DESK-12 ("GPU preference (high performance)", planned for Phase 5) into this gap closure; the planner moved DESK-12 to Phase 2 in ROADMAP.md and REQUIREMENTS.md when these plans were written.

<objective>
Wire the legacy GPU preference (SSDHG.Configure / GraphicPreference.EnsureHighPerformance): read Engine.json GraphicPreference, write UserGpuPreferences for sucrose.exe before any renderer starts, log the adapter each renderer's Direct3D device uses, and record DESK-12 as shipped.

Purpose: without it libmpv's D3D11 device lands on DXGI adapter 0, which is the Intel UHD whenever the internal panel is primary; that GPU cannot render the 4K60 HEVC theme (98 % 3D, A/V desync, about 0.28x playback). Root cause: `.planning/debug/renderer-runs-on-power-saving-gpu.md`.
Output: GraphicPreference reading with fixture tests, service and renderer wiring, docs.

Not in this plan (open maintainer decision, not parity): passing mpv `d3d11-adapter` chosen through EnumAdapterByGpuPreference so the GPU no longer depends on which display is primary. Do not add it; it is listed under "Open decisions" below.
</objective>

From plan 02-17 (read crates/sucrose-platform/src/lib.rs and crates/sucrose-core/src/settings.rs, do not re-derive):
- `GpuPreference { Default, PowerSaving, HighPerformance }` in sucrose-core settings, default HighPerformance, with `from_legacy_name`, `from_legacy_index` and `legacy_ordinal`.
- `Platform::set_gpu_preference(&self, exe: &Path, preference: GpuPreference) -> Result<GpuPreferenceChange, PlatformError>` with `GpuPreferenceChange { Written, Unchanged }`; it writes HKCU\Software\Microsoft\DirectX\UserGpuPreferences with the legacy merge rules (other pairs kept, unchanged value skipped).
- `Platform::gpu_adapters(&self) -> Vec<GpuAdapter { name, luid, dedicated_video_memory_mb }>`: every adapter, to name a LUID; `luid` is in the typeperf form. Its order is NOT evidence of which adapter a device uses: never log its first entry as the adapter in use.
- `Platform::default_gpu_adapter(&self) -> Option<GpuAdapter>`: the adapter read back from a Direct3D 11 device created with no adapter named, i.e. the adapter libmpv's video device gets (config.rs sets no d3d11-adapter); None when unknown.
- Ground truth for which adapter a process really uses: the per-process GPU Engine counters, `typeperf.exe '\GPU Engine(*)\Utilization Percentage'`, instance names `pid_<pid>_luid_0x<hi>_0x<lo>_phys_<n>_eng_<n>_engtype_<type>` (the same LUID text as GpuAdapter.luid; checked against live typeperf output at planning time). Task Manager's "GPU engine" column reads the same counters.
- `Capabilities.gpu_preference`: true on Windows, false on macOS and Linux.

Legacy behavior:
- Engine.json key GraphicPreference, enum HighPerformanceType { Default, PowerSaving, HighPerformance } (docs/legacy/formats.md §1.3 and the enum list), default HighPerformance; the registry number is the enum ordinal.

Existing Rust facts:
- `Properties::get_enum(key, default, from_name, from_index)` in crates/sucrose-config/src/legacy.rs; `EngineSettings::from_properties`.
- service.rs `run()`: `plan_wallpapers()` -> `Plan { job, status, app_visible, fullscreen, pause }`; the first renderers spawn in `fleet.apply(diff(&[], &monitors), ..)` inside `if let Some(screen) = fleet.job...`. `Supervisor::new` spawns renderers from `std::env::current_exe()` (supervisor.rs), so one value covers the service and all renderers.
- render.rs `run()`: `DesktopSurface::attach(rect)` then `start_engine(surface.native_handle(), &assignment)`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Legacy Engine.json -> service | A user-editable file decides which GPU preference is written |
| Service -> the user's registry (HKCU) | The service writes one value through Platform::set_gpu_preference (registry-write mitigations: T-02-38 in plan 02-17) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-39 | Tampering | Engine.json GraphicPreference | low | mitigate | Only the three enum names or ordinals 0..2 are accepted; anything else falls back to the legacy default HighPerformance, so a corrupt file cannot write an arbitrary number |
| T-02-40 | Information Disclosure | service and renderer logs | low | mitigate | Logs carry the preference, the outcome and the adapter name/LUID only, never the exe path or other registry content |
| T-02-SC | Tampering | crates.io dependencies | high | mitigate | No crate is added: the service, renderer and sucrose-config use workspace crates only; `cargo deny check` runs in CI. Any new crate would need `gsd_run query package-legitimacy check --ecosystem crates` and a blocking human checkpoint first |
</threat_model>
