## Phase Goal

ROADMAP goal: *An existing user's selected video theme plays behind the desktop icons on every monitor on Windows through libmpv, survives shell and monitor changes, and pauses for fullscreen apps.*

This plan's slice (UAT gaps G-02-2d and G-02-2a): **monitor and shell changes are noticed when they happen, and the video comes back in front of the shell's wallpaper after explorer.exe restarts.**

<objective>
Make the platform event loop hand over every event that a sent (non-queued) window message queued, so a non-primary monitor unplug and TaskbarCreated reach the service at once (G-02-2d). Then make the Raised-layout attach wait for the shell's wallpaper WorkerW, check the Progman child order in verify(), and keep that order with an event-driven WinEvent guard (G-02-2a).

Purpose: success criterion 2 ("survives an explorer.exe restart and monitors being plugged/unplugged") failed in UAT test 2. Root causes: `.planning/debug/non-primary-monitor-unplug-not-detected.md` and `.planning/debug/explorer-restart-wallpaper-not-restored.md`.
Output: a drained EventLoop with sent-message regression tests, `layout::raised_order`, a WorkerW-aware attach with an order guard, FEATURES notes.

Coupling: once TaskbarCreated is no longer stranded (Task 1), the service respawns renderers right when explorer broadcasts it, while explorer's desktop thread may still be initializing (in UAT the broadcast was most likely stranded for about 30 s by the G-02-2d bug). Tasks 2 and 3 therefore must handle a Progman that answers 0x052C late.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Other processes -> service and renderer windows | Any process of the session can send window messages to the hidden loop window |
| explorer.exe -> renderer (WinEvent callbacks) | Window events of the shell process run code on the renderer thread |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-35 | Denial of Service | event_loop.rs drain post | low | mitigate | WM_DRAIN is posted at most once per pending batch (DRAIN_POSTED), so a flood of sent display messages produces a bounded number of posts; the handler work per DisplayChanged is only a debounce timer restart |
| T-02-36 | Denial of Service | surface.rs order guard | low | mitigate | Hook limited to the Progman owner process and events 0x8000..0x8004, O(1) filtering per callback; at most 10 restores per 60 s, then the guard unhooks with a warning |
| T-02-37 | Tampering | surface.rs order guard and verify | low | mitigate | The guard only reorders the renderer's own surface (SetWindowPos on its own window); it never moves, resizes, restyles or destroys a shell window, so a fake WorkerW from another process can at most trigger a bounded number of own-window reorders |
| T-02-SC | Tampering | crates.io dependencies | high | mitigate | No crate is added: only the `Win32_UI_Accessibility` feature of the already pinned `windows` 0.62.2 crate; `cargo deny check` runs in CI. Any new crate would need `gsd_run query package-legitimacy check --ecosystem crates` and a blocking human checkpoint first |
</threat_model>
