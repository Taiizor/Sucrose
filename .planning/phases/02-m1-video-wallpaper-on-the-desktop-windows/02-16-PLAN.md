## Phase Goal

ROADMAP goal: *An existing user's selected video theme plays behind the desktop icons on every monitor on Windows through libmpv, survives shell and monitor changes, and pauses for fullscreen apps.*

This plan's slice (UAT gaps G-02-2d and G-02-2a): **monitor and shell changes are noticed when they happen, and the video comes back in front of the shell's wallpaper after explorer.exe restarts.**

<objective>
Make the platform event loop hand over every event that a sent (non-queued) window message queued, so a non-primary monitor unplug and TaskbarCreated reach the service at once (G-02-2d). Then make the Raised-layout attach wait for the shell's wallpaper WorkerW, check the Progman child order in verify(), and keep that order with an event-driven WinEvent guard (G-02-2a).

Purpose: success criterion 2 ("survives an explorer.exe restart and monitors being plugged/unplugged") failed in UAT test 2. Root causes: `.planning/debug/non-primary-monitor-unplug-not-detected.md` and `.planning/debug/explorer-restart-wallpaper-not-restored.md`.
Output: a drained EventLoop with sent-message regression tests, `layout::raised_order`, a WorkerW-aware attach with an order guard, FEATURES notes, and corrected render.rs comments on the surface-lost exit (see "Surface loss without WM_DESTROY" below).

Coupling: once TaskbarCreated is no longer stranded (Task 1), the service respawns renderers right when explorer broadcasts it, while explorer's desktop thread may still be initializing (in UAT the broadcast was most likely stranded for about 30 s by the G-02-2d bug). Tasks 2 and 3 therefore must handle a Progman that answers 0x052C late.
</objective>

## Surface loss without WM_DESTROY (UAT G-02-2a artifact apps/sucrose/src/render.rs)

The debug session (secondary finding) showed that killing explorer.exe sends no WM_DESTROY to the surfaces, so the renderer's `EXIT_SURFACE_LOST` path (exit 3, taken when `surface_proc` sees a WM_DESTROY the renderer did not cause itself) never fired, and the old renderers ran on until TaskbarCreated. This plan keeps that exit path's behavior unchanged and corrects only its comments (Task 3), because the current path is correct without that message:

- Recovery never waits for it. Per D-11 a shell restart is detected only through TaskbarCreated: the service's `shell_restarted` tells every renderer to close, and `decide_exit` (supervisor.rs, `ShellRestart`) starts each closed slot again whatever its exit code. In UAT the old renderers exited 0 on that request and were replaced; what failed was the ~30 s delay of TaskbarCreated (G-02-2d, Task 1) and the hidden new surfaces (Tasks 2 and 3), not the missing WM_DESTROY.
- Where Windows does destroy the surface (a WM_DESTROY the renderer's own drop did not cause), exit 3 is still the right outcome: `decide_exit` counts it as part of the shell restart inside `SHELL_RESTART_WINDOW`, or else as a lost-surface strike with its own budget. Nothing else depends on it.
- What remains: between a killed shell and the new shell's TaskbarCreated, the old renderers keep playing into a surface that is not shown. After Task 1 this lasts only until the new shell broadcasts TaskbarCreated; if no shell comes back, they run until Quit. The legacy app by default (CrashExplorer false) does not react to a dead shell either, and D-11 rules out polling for one, so this plan adds no other detection (no UAT item asks for one).

## The 500 ms restart delay stays (UAT G-02-2a artifact apps/sucrose/src/service.rs)

UAT names the fixed 500 ms between TaskbarCreated and the new renderers as part of the trigger: `shell_restarted` (service.rs) asks each connected renderer to close, and `decide_exit` (supervisor.rs, `ShellRestart` branch) starts each closed slot again after `FIRST_BACKOFF` (500 ms); a slot with no running renderer starts at once. This plan accepts that delay unchanged and edits neither file, because after Tasks 2 and 3 the start time no longer decides whether the video is visible:

- The attach no longer assumes Progman is ready when the renderer starts. Task 2 resends 0x052C and retries with backoff until the shell's wallpaper WorkerW exists, for up to the 10 s `ATTACH_TIMEOUT`, and verify() rejects an attach with the WorkerW above the surface. A renderer that starts 500 ms after TaskbarCreated waits inside that window instead of attaching too early.
- A shell slower than 10 s gets the last-resort attach under DefView, and the Task 3 order guard puts the surface back above the WorkerW as soon as the shell creates, shows or reorders it.
- A longer fixed delay would only be a guess at how long explorer's desktop thread needs (in UAT it had not answered 0x052C within 1 s), would slow every shell restart even when the shell is quick, and would still lose the race against a slower shell; D-11 rules out polling for readiness. Waiting for the WorkerW itself, inside the renderer (Task 2), replaces that guess.
- `FIRST_BACKOFF` is also the first step of the crash and lost-surface backoff (`RestartBudget::allow`), and `shell_restart_respawns_each_closed_slot_once_whatever_its_exit_code` pins the 500 ms; changing the constant would change those restarts too, for no gain.

The Task 3 human check (two explorer restarts in a row) confirms on the machine that the video comes back with the delay unchanged.
