## Phase Goal

ROADMAP goal: *An existing user's selected video theme plays behind the desktop icons on every monitor on Windows through libmpv, survives shell and monitor changes, and pauses for fullscreen apps.*

This plan's slice (UAT gap G-02-2b and the root cause of G-02-6, platform half): **Sucrose can ask Windows for a GPU for its own exe exactly as the C# app does, can name the GPU adapters, and can tell which adapter a Direct3D 11 device of the process really gets.** The maintainer decided in UAT (test 6, option 1) to pull DESK-12 ("GPU preference (high performance)", planned for Phase 5) into this gap closure; the planner moved DESK-12 to Phase 2 in ROADMAP.md and REQUIREMENTS.md when these plans were written. Plan 02-18 (the wiring half) reads Engine.json GraphicPreference, calls this before the first renderer starts, logs each renderer's video adapter (default_gpu_adapter) and records DESK-12 as shipped; plan 02-21 uses the adapter list in `cargo xtask measure`.

<objective>
Port the platform side of the legacy GPU preference (SSDHG.Configure / GraphicPreference.EnsureHighPerformance): the `GpuPreference` setting enum, a `Platform` method that writes UserGpuPreferences for an exe with the legacy merge semantics, the `gpu_preference` capability, the DXGI adapter list, and the adapter read back from a Direct3D 11 device created the way libmpv creates its own (UAT G-02-2b: "Log the D3D adapter the renderer actually uses").

Purpose: without it libmpv's D3D11 device lands on DXGI adapter 0, which is the Intel UHD whenever the internal panel is primary; that GPU cannot render the 4K60 HEVC theme (98 % 3D, A/V desync, about 0.28x playback). Root cause: `.planning/debug/renderer-runs-on-power-saving-gpu.md`.
Output: `GpuPreference` in sucrose-core; the `sucrose-platform` GPU module, trait methods and capability, proven by pure and scratch-registry tests. Plan 02-18 calls them from the service and the renderer.

Not in this plan (open maintainer decision, not parity): passing mpv `d3d11-adapter` chosen through EnumAdapterByGpuPreference. Do not add it; plan 02-18 lists it under "Open decisions".
</objective>

<interfaces>
Legacy behavior (src/Shared/Sucrose.Shared.Space/Extension/GraphicPreference.cs, read-only reference):
- Key HKCU\Software\Microsoft\DirectX\UserGpuPreferences (created when missing); value name = the exe's full path; type REG_SZ; data "Key=Value;Key=Value;" with a trailing ';'.
- Parse: split on ';' dropping empty parts, trim each part, split at the first '='; keep a pair only when key and value are both non-empty; keys compare case-insensitively (a later duplicate overwrites the earlier value but keeps its position and spelling).
- Current preference = the GpuPreference pair parsed as an integer that is 0, 1 or 2; anything else (missing, not a number, out of range) counts as Default (0). When it equals the wanted ordinal nothing is written (so Default with no value writes nothing).
- Otherwise set GpuPreference (existing key spelling kept, else appended as "GpuPreference") and write all pairs back joined with ';' plus a trailing ';'. A non-string value counts as missing.
- Engine.json key GraphicPreference, enum HighPerformanceType { Default, PowerSaving, HighPerformance } (docs/legacy/formats.md §1.3 and the enum list), default HighPerformance; the registry number is the enum ordinal.

Existing Rust facts:
- `legacy_enum!` / `legacy_index!` in crates/sucrose-core/src/settings.rs generate ALL, legacy_name, from_legacy_name, from_legacy_index.
- `Platform` trait (crates/sucrose-platform/src/lib.rs) with default methods; `Capabilities { desktop_wallpaper, embed_application, fullscreen_detection }`; Windows impl `Current` in os_windows.rs.
- typeperf GPU instance names carry the adapter as `luid_0x00000000_0x0000A1B2` (HighPart, then LowPart, 8 uppercase hex digits each); use the same text for `GpuAdapter.luid` so logs and `cargo xtask measure` match.
- windows crate 0.62.2 features: `Win32_System_Registry` (RegCreateKeyExW, RegQueryValueExW, RegSetValueExW, RegCloseKey, RegDeleteTreeW, HKEY_CURRENT_USER), `Win32_Graphics_Dxgi` (CreateDXGIFactory1, IDXGIFactory1::EnumAdapters1, IDXGIAdapter1::GetDesc1, DXGI_ADAPTER_DESC1, DXGI_ERROR_NOT_FOUND, IDXGIDevice::GetAdapter, IDXGIAdapter::GetDesc), `Win32_Graphics_Direct3D` (D3D_DRIVER_TYPE_HARDWARE) and `Win32_Graphics_Direct3D11` (D3D11CreateDevice, D3D11_SDK_VERSION, ID3D11Device); add `Win32_Graphics_Dxgi_Common` only if the compiler asks for it. `Win32_System_Performance` is already enabled (QueryPerformanceCounter).
- Which adapter libmpv's video device uses: crates/sucrose-engine-mpv/src/config.rs sets vo=gpu, gpu-context=d3d11 and no d3d11-adapter (debug session), and with no adapter name libmpv creates its D3D11 device without naming an adapter (the pinned libmpv-2.dll carries "Will fall back to the default adapter"). A D3D11 device created the same way in the same process therefore gets the same adapter, after whatever GPU preference the OS applies; reading it back from that device is the evidence. The DXGI enumeration index is not: whether the per-app UserGpuPreferences value changes the EnumAdapters1 order is not established here, so the first list entry must never be reported as the adapter in use. The per-process GPU Engine counters (typeperf instance `pid_<pid>_luid_<hi>_<lo>_...`) are the OS's own record of it; plan 02-18 cross-checks the two on the machine.
