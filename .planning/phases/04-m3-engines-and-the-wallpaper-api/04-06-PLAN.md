## Phase Goal

ROADMAP goal (not yet a user story; `/gsd-mvp-phase 4` can convert it, this plan does not invent one): *Every wallpaper type plays on Windows on every engine that supports it, existing web wallpapers work unchanged with the C#-compatible JavaScript API, and display modes, property editing and the performance rules match or improve on the C# app.*

**Planning round:** Round A of the five D-31 planning rounds (04-CONTEXT D-31 "Planning rounds"): D-31 slice 1 only — the engine trait, detection and per-type choice with fallback, CEF bundled through `cargo xtask fetch-engines`, the virtual origin (D-14) and the JavaScript API (PropertyListener, SucroseCompatible.json, the first system data), proven with the maintainer's 8 Web themes and the fixture pages. Rounds B–E are planned after Round A has executed.

This plan's slice: **the virtual origin** — every web wallpaper is served from `https://sucrose.wallpaper.engine/` through one tested resolver behind CEF's scheme handler, and path traversal is refused. WebView2 (Round B) puts its WebResourceRequested adapter on the same resolver.

## Settled one-way decision (reversibility gate)

D-14 is one-way: after release, every web wallpaper's localStorage, IndexedDB and cookies are bound to this origin. The maintainer confirmed on 2026-11-25 one shared origin `https://sucrose.wallpaper.engine/` for all themes (per-theme subdomains were offered and declined). This plan uses exactly that origin and gets no new checkpoint:decision; if anything would need another origin, stop and ask the maintainer.

**Requirement status of this plan:** SEC-02 has no other Round A part: this plan marks it Complete when both verifies pass (Complete rule: the resolver vector tests and the CEF traversal run pass → `requirements-completed: [SEC-02]`; a failure or an incomplete plan → `[]` and SEC-02 stays Pending; Round B's WebView2 adapter must call the same resolver and must not reopen it). ENG-03 (Round B) and TYPE-03 (04-20) are not marked here.

## Executor environment (applies to every task)

- Run every command from the repository root in WSL. `cargo` is the Windows toolchain behind a wrapper and builds Windows binaries; never install a Linux Rust toolchain. Bun is the only JS runtime; no node/npm/npx for project work.
- `src/` (C#) is read-only reference: read it, never edit or build it.
- The maintainer's real data is read-only: `%APPDATA%\Sucrose` (Setting, Cache, Log, Showcase) and the library `H:\Sucrose` (`/mnt/h/Sucrose`). Read it, never write, rename, move or delete anything there. Automated runs never turn Corrupt Themes on.
- When you start `sucrose.exe` or `sucrose-portal.exe`: set `SUCROSE_DATA_DIR="$(wslpath -w target/<scratch folder>)"` and `WSLENV=SUCROSE_DATA_DIR` (add `:SUCROSE_LOG` when you set `SUCROSE_LOG`); start the Portal with `--no-focus`; never synthesize mouse or keyboard input; capture windows only with `.claude/skills/port-feature/capture.ps1` (PrintWindow; never edit it, add no PowerShell, shell or batch script to the repository — new automation goes into `xtask`); stop what you started with `taskkill.exe /IM sucrose-portal.exe /F` and `taskkill.exe /IM sucrose.exe /F` (CEF subprocesses are `sucrose.exe` too, so this ends them; if 04-01 took the D-32 fallback also `taskkill.exe /IM sucrose-cef.exe /F`).
