## Phase Goal

ROADMAP goal (not yet a user story; `/gsd-mvp-phase 3` can convert it, this plan does not invent one): *The service and the Portal work as one app: the user picks a theme in the Portal's library, "Use" applies it through the service, settings migrate from the C# install and persist, and Sucrose can start with the OS.*

This gap-closure plan's slice: **images the Portal stops showing really leave GPUI**, the root cause of the paging-memory gap (SC5, UI-07). The hover-preview fix of 03-28 depends on it, because an animating preview puts every frame into the atlas.

<objective>
Find and fix the growth source of the 500-theme paging run (03-VERIFICATION gap 2) with evidence: every `cx.drop_image(image, None)`-style release in the Portal that runs while the window is being updated (the hover leave handler, page change, search, settings change, background change) misses that window, because GPUI takes the window out of `App.windows` during its update and reaches it only through `Some(window)` (gpui-pre 0.3.12 `src/app.rs` around line 3214, doc comment of `App::drop_image`). Each missed image keeps its atlas tile, and a leaked tile keeps its whole 1024 x 1024 BGRA atlas texture (4 MiB) alive while thumbnails churn through it (gpui-pre-windows 0.3.12 `directx_atlas.rs`: a texture is freed only when its last tile is removed). Route every release through one deferred helper, prove both the cause and the fix with GPUI tests, and log the Portal's own image counts for the reruns.

Purpose: UI-07 / SC5 gap 2 (root cause and fix); prerequisite for 03-28 (animated previews) and the D-25 reruns 03-37 and 03-38.
Output: `apps/sucrose-portal/src/atlas.rs`, the three call sites moved to it, GPUI tests, a richer "page shown" debug line, docs/GPUI.md lesson.
</objective>
