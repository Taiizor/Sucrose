## Run rules (binding)

- Prepare everything first (release build, scratch data, commands) and only then present a checkpoint; nothing the maintainer has to watch runs before the checkpoint text is ready.
- Visual checks on DISPLAY1. DISPLAY9 is an intentional virtual display; when the migrated selected theme plays, two renderers are expected (one per display).
- Focus: the unattended smoke starts the Portal with `--no-focus`; the runs the maintainer drives start it WITH focus (a hand-driven run is not an automated check; CLAUDE.md scopes no-focus to automated checks). No input is ever synthesized.
- App lifetime: while a checkpoint is presented the release `sucrose-portal.exe` and the release `sucrose.exe` it started (and its renderers) are running; the checkpoint text says so. The continuation that receives the last reply stops them with the two taskkill commands and confirms with `tasklist.exe`.
- Skips are honest: a reply that skips (for example "geçelim", "skip") ends the plan: stop the apps, write a halted SUMMARY (`status: halted`) with the reply verbatim, `requirements-completed: []`, `frame_extension: undetermined`, `backdrop_next: replan` and a "## Backdrop lead" section that says the check was skipped and quotes the reply, docs unchanged.
- The OS scrollbar setting (Settings > Accessibility > Visual effects > Always show scrollbars; registry `HKCU\Control Panel\Accessibility` value `DynamicScrollbars`, 1 or absent = auto-hide, 0 = always show) is only read with `reg.exe query`; only the maintainer changes it.
