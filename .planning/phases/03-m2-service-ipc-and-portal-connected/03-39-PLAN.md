## Growth-source follow-ups (binding when a D-25 rerun fails)

03-27 fixes the leading cause of the 500-theme growth (images released inside a window update stayed in GPUI's atlas); 03-40 makes each rerun attribute what still grows. When both scenarios pass, the atlas cause is recorded as confirmed and nothing below applies. When a scenario fails on working set or private bytes, its attribution verdict selects exactly one follow-up: Task 1 records it in docs/MEASUREMENTS.md and docs/GPUI.md, and Task 3's unmet precondition returns it, with the numbers, as the scope of the next gap round (`/gsd-plan-phase 3 --gaps`). This plan does not carry them out: each changes code that a rerun must judge again, and F-3's allocator option needs the maintainer's decision first.

**Round scope.** The follow-ups have no tasks in this round on purpose: which one applies is known only after the reruns, and each needs its own plan. So when a rerun fails, this round ends with SC5 and UI-07 open: UI-07 stays Pending in .planning/REQUIREMENTS.md, 03-VERIFICATION.md gap 2 stays failed for the next /gsd-verify-work, and the next gap round plans the selected follow-up with tasks, files and acceptance criteria. That outcome is recorded where it survives the stop: in docs/MEASUREMENTS.md (Task 1's reading paragraph says "SC5 stays open for the next gap round"), in docs/GPUI.md, and in Task 3's checkpoint return, which the orchestrator carries into the phase record. This plan's SUMMARY is deliberately not written in that case, because the executor's update step would mark UI-07 Complete from it.
