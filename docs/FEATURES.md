# Features and parity

Every feature of the C# app, where it goes in the rewrite, and what each OS allows. This is the parity checklist for M7. Exact legacy behavior (keys, defaults, timings, APIs) is in `docs/legacy/`: `portal.md`, `services.md`, `engines.md`, `formats.md`, `lock-screen.md`.

- **Status:** ⬜ not started · 🟨 in progress · ✅ ported · ➖ dropped (needs a `DECISIONS.md` entry)
- **Platform columns** (planned support): ✅ full · ⚠️ limited · ❌ not possible · ? not investigated yet
- When you port a row: set the status, correct the platform cells with what you learned, and note behavior changes and improvements.

| GIF | ✅ | ✅ | ✅ | Built-in renderer replaces Vexana/Xavier; add APNG/WebP. Legacy default mpv. Rust (Phase 4 Round B, 04-30, Windows): the built-in renderer (crate `sucrose-engine-gif`) plays a GIF theme set to XavierLive or VexanaLive: the animation is decoded lazily on a thread of its own (one frame in flight and a bounded channel of 2, never the whole animation in memory), a frame is scaled down to the surface size but never up and shown with Direct2D on a child window of the desktop surface, filling it; a frame delay of 0 plays at 100 ms (the legacy XamlAnimatedGif rule). Loop on starts again at frame 0 after the last frame, loop off stops on the last frame (legacy Xavier plays it once); a surface that changes size re-opens the decoder at the frame on screen, a move re-uses it. The file type is read from its first bytes, and a damaged or hostile file is a start failure with a reason, never a crash. There is no audio and no clock yet: two monitors playing the same GIF run independently until the follower round (D-04). The migrated Engine.Gif = MpvPlayerLive keeps playing GIFs on mpv, and Gif cards are usable in the Portal (D-17 lifted for Gif). Rust (04-31): the Engine section's stretch mode reaches the renderer at start and while it plays and places the frame as engines.md §3 says for an image: None centres it at 1:1 (cropped to the centre when larger than the surface), Fill stretches to the surface, Uniform letterboxes with black bars, UniformToFill crops through the source rectangle; with the same aspect ratio the last three give the same full rectangle. The decoder prepares frames for the mode (Fill and Uniform scaled down to fit, UniformToFill scaled down only as far as it still covers the surface, None keeping only the centre that fits), so memory stays bounded; a mode change that needs another preparation re-opens the decoder at the frame on screen. Where Direct2D cannot create its render target a GDI `StretchDIBits` presenter draws the same rectangles, and a Direct2D target that is lost (D2DERR_RECREATE_TARGET) three times in a row moves drawing to GDI (a success in between starts the count again); the log names the presenter (`gif presenter=Direct2D` or `gif presenter=Gdi`) and the rectangles (`gif fit stretch=... dest=[...] src=[...]`, debug). Rust (04-32): animated PNG (APNG) and animated WebP play on the same renderer; the format is read from the bytes (a PNG with an acTL chunk, a RIFF WEBP, a GIF named .png is still a GIF), the frames decode lazily through the same decoder with the same scaling, the log says `gif opened format=Apng` or `format=WebP`, and a plain PNG or a still WebP is shown as one frame. Frame delay rule, the same for GIF, APNG and WebP so equal inputs time equally: a delay of 0 plays at 100 ms (the legacy XamlAnimatedGif rule, which has no other threshold), any other delay is used as it is, in whole milliseconds (a GIF stores hundredths of a second). A file with exactly one frame is shown once and starts no frame timer, whatever loop says; sources above 8192 × 8192 are refused from their header before any frame is decoded, a missing, empty, truncated or frameless file ends the wallpaper with a reason. Not covered: an APNG with 16-bit colour is a start failure (the decoder composites 8-bit only). | 🟨 |
| Web (local HTML) | ✅ | ✅ | ✅ | WebView2/CEF (Win), WKWebView/CEF (mac), WebKitGTK/CEF (Linux). JS API must stay compatible. Rust (Phase 4 Round A, Windows): CEF 156 windowed child of the desktop surface, pumped on the surface thread with the external message pump (D-036); the page is served from `https://sucrose.wallpaper.engine/` (D-14, one shared origin for every theme, no local port, no `file://`) through a CEF scheme handler for that host only, over one resolver (theme folder first, then the generated-content folder; `Range` requests answered with 206/416 so videos seek; legacy CORS `Access-Control-Allow-Origin: *` kept; MIME table of the legacy server plus `.mjs` and `.wasm`); a Web theme whose Source is an address plays with the URL path from slice 3; the property and non-data compatible calls are done (see the Web wallpaper API rows), system data and audio are not. Web data (D-33, D-35, D-040): the CEF wallpaper of the primary monitor keeps its localStorage and cookies in `<data_dir>/Web/Cef`, held by a lock file while it runs (outside `Cache`, so cache cleaning never deletes it; the C# `Cache/CefSharp` folder is never read); every other concurrent CEF wallpaper runs on an ephemeral profile (`Cache/WebEphemeral/Cef/<slot>`) that is emptied at its start, so a wallpaper on another monitor starts empty every run. Behavior change (D-12): TLS certificates are validated; the legacy CEF accepted every certificate. Closing (theme switch, stop): the renderer closes the CEF browser itself and CEF never sends its default close message, which for a windowed browser is `WM_CLOSE` to the browser's top-level window; under the desktop that window is the shell's Progman, whose `WM_CLOSE` is the Shut Down Windows dialog (04-20 defect). A `window.close()` from the page is ignored and the wallpaper stays open (a wallpaper is not a browser tab). The legacy app ended its CefSharp process with `Process.Kill` on a switch, so it never closed the browser through CEF. Rust (Phase 4 Round B, 04-22): WebView2 is the second web engine (the user-installed Runtime, static loader linked): its environment and controller are a child of the desktop surface on the surface thread, black background, physical-pixel bounds scaled by the monitor DPI; every request of the same virtual origin goes through one reply planner shared with CEF (`sucrose_engine_web::serve::plan`: the same resolver, 404 for every refusal, the same CORS headers), and a single `Range` request gets the reply the planner decides, as on CEF: 206 with `Content-Range` and `Accept-Ranges: bytes`, 416 for a range past the end, 200 with the whole length without a `Range` (04-23). A range body is a memory stream of at most 4 MiB (`MAX_RANGE_BODY`) whose `Content-Range` names exactly the bytes it carries, so a media element seeks by asking again; a whole file streams from disk, and `HEAD` gets the headers only. Round B (04-22, 04-23): WebView2 hosts Web themes on the same origin and resolver; range replies; the traversal fixture refuses every vector on WebView2 too (page calls, system data and input follow in later Round B plans). Its persistent profile is `<data_dir>/Web/WebView2`, kept by the primary monitor's renderer under the same rule (D-040; other renderers get `Cache/WebEphemeral/WebView2/<slot>`); downloads are cancelled and the page gets no host object and no message channel; the close closes the controller first and posts nothing to any window. Behavior change (D-041, debug session webview2-browser-exit-slow, 2026-11-27, maintainer decision): WebView2 wallpapers run without Edge SmartScreen by default (Sucrose's own switches add `msSmartScreenProtection` to `disable-features`); the legacy WebView2 engine always ran with it. SmartScreen setting (261128-0du, 2026-11-28): `Engine.WebViewSmartScreen` (default off; a missing, non-boolean or migrated value reads off, the legacy app has no such key) is the WebView2 SmartScreen switch directly under the WebView2 row of the Web Engine Settings group, with an info hint that on sends the wallpaper's address to Microsoft and can make a quick switch slow; on, Sucrose's own WebView2 switches leave `msSmartScreenProtection` out (a user `disable-features` that names it keeps it) and the switch editor no longer lists it among Sucrose's own; saving it while a WebView2 wallpaper runs opens the Restart wallpapers prompt for the WebView2 wallpapers only (Restart now restarts those, Later applies it at the next start); CEF is unchanged. With SmartScreen on, the first navigation of a profile folder that was never used sends a SmartScreen check with the wallpaper's address to Microsoft, and a close while it is in flight holds the browser process about 6 s, so a quick theme switch waited that long for the next page; with SmartScreen off the browser exits about 0.25 s after the close and a switch takes under 1 s on two monitors, close to CEF (which has no SmartScreen). Turning the setting on brings the about 6 s close back for such a switch (the renderer waits at most 1 s, then the next renderer may start without its profile folder). WebView2 is offered for Web themes only for now. CEF fixes (debug session cef-web-themes-stuck-loading, 2026-11-27): the sucrose binary now embeds an application manifest with the Windows 10 `supportedOS` entry (`apps/sucrose/build.rs`, through the MSVC linker); without it CEF's GPU process, which is the same executable (D-036), crashed on its first command buffer, Chromium turned GL off after three crashes and no page got WebGL, so three.js themes stayed on their loading screens (04-37 D1, D6 on CEF, the 04-20 "SucrosePropertyListener is not defined" of a theme that installs its listener after creating its WebGL renderer). The CEF browser process also gets `--user-data-dir` set to its profile folder (the folder CEF already used, so nothing moves): without it Chrome's startup check dropped the legacy `disable-web-security` default, and cross-origin requests that legacy CefSharp and WebView2 allow failed with a CORS error (04-20 Test Sucrose API); with in-memory caches (no profile folder) web security stays on. The CEF scheme handler implements Skip, which CEF's loader calls for every `Range` that starts past byte 0: before, those requests failed, so a video whose index sits at the end of its file never played and seeking did not work (04-37 D4); WebView2 never had this step. H.264 and AAC do not play on CEF (the CEF build has no proprietary codecs, as legacy CefSharp); VP8, VP9 and AV1 do. CEF browser window (debug session web-loading-white-border, 2026-11-27; every CEF wallpaper: Web, URL, YouTube and the generated pages): the window is created hidden, and Chromium's widget window inside it (`Chrome_WidgetWin_1`) loses its `WS_THICKFRAME` style before the window is shown. Before, Windows painted the classic 7 px sizing frame of that child window into the desktop surface, at the creation and again on later non-client messages, and nothing painted over it until the GPU process showed the page's first frame, so a light border stood around the screen for 1-3 s (longer on a cold start) while a wallpaper loaded (04-37 D2). The legacy CefSharp engine used the windowed `CefSharp.Wpf.HwndHost` control, a windowed CEF browser inside the engine's WPF window (its CefSettings also set `WindowlessRenderingEnabled`, which only allows off-screen browsers; it made none); WebView2's windows have no sizing frame and showed none in the same checks. CEF focus (debug session cef-start-steals-focus, 2026-11-27, 04-37 D12; every CEF wallpaper): starting a CEF wallpaper no longer takes the keyboard focus or the foreground. Before, CEF focused its widget twice while the browser was made: Chromium showed the widget as an activating window (`SW_SHOWNORMAL`, then `SetForegroundWindow` and `SetFocus`), and CEF focuses the browser whenever the host loads an address (`OnSetFocus` with `FOCUS_SOURCE_NAVIGATION`). The surface shares the shell's input state, so that took the desktop's keyboard focus and activated Progman, and when the new renderer was allowed to set the foreground (for example when it was started while its launcher was in front) the user's window lost the foreground and the next keys went to the wallpaper. The browser window is now created with `WS_EX_NOACTIVATE` (CEF shows the widget without activating or focusing it and takes the style off the widget again) and a focus handler cancels the navigation focus (a popup of the page keeps CEF's default), the two defaults of the legacy `CefSharp.Wpf.HwndHost` control (its focus handler and `ActivateBrowserOnCreation` off). The page gets the keyboard focus from the first forwarded click, which Chromium answers by focusing itself, so the D11 rule still gives each key one channel; until that click the page has no keyboard focus, as in the legacy app, and keys are posted to it (`OnlyKeyboard` still sends its one-time click first). WebView2 never took the focus. User agent (261127-uov, 2026-11-27): General.UserAgent (legacy default `Sucrose/2.4 (Windows NT 10.0; Wallpaper Engine) SucroseWebKit`) is applied on both engines as in the legacy app (`CefSettings.UserAgent`, `CoreWebView2.Settings.UserAgent`). CEF gets it through its `user_agent` setting (no switch was needed), WebView2 through `ICoreWebView2Settings2::SetUserAgent` before the first navigation. It is the `User-Agent` header and `navigator.userAgent` of every page and frame (Web, URL, YouTube and the generated Gif and Video pages). It is read when the job is made, so a change applies at the next start (Restart now, the next Use). New: an empty or blank value, or one with a control character, keeps the engine's own user agent (the control-character case with a WARN that gives only the length; the legacy app passed such a value on), a failed `SetUserAgent` is a WARN and the page plays with WebView2's own, and players get none. With a `user-agent` switch in the user's CefArguments or WebArguments, observed on 2026-11-27: on CEF the switch wins over General.UserAgent (the page reports the switch value), on WebView2 General.UserAgent wins over the switch (SetUserAgent runs after the browser is started with it). Checked through CDP on both engines (a probe value, the legacy default, a blank value that gives each engine's own `Chrome/` agent). | 🟨 |
