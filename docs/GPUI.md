# GPUI notes

Practical notes for the UI (`gpui-kit`). GPUI documentation is thin; read the source of the pinned crates in the Cargo registry (`$CARGO_HOME/registry/src/…/gpui-kit-*`, `gpui-component-*`, `gpui-base-*`, `gpui-pre-*`) when an API is unclear.

## Versions

- `gpui-kit 0.10` re-exports GPUI and pins a Zed snapshot published as `gpui-pre 0.3.12`. This is **not** the official `gpui` 0.2.x on crates.io. Always depend on `gpui-kit` only, with an exact version, and upgrade deliberately (read its changelog, rebuild the prototype, compare screenshots).
- `use gpui_kit::*;` is GPUI. Components: `gpui_kit::component::…`. Icons: `gpui_kit::assets::IconName` (Lucide). `gpui_kit::open_window` mounts the base `Root`; call `gpui_kit::init(cx)` first.

## Prototype

`exp/GPUI/Sucrose.Portal` is a throwaway experiment that partly recreates the current Portal (library, store, settings, status bar) with real data, read-only. It is not the base of `apps/sucrose-portal`. It never evicts decoded thumbnails or releases them from GPUI's image atlas, so memory keeps growing while paging through the store: the real Portal needs a bounded thumbnail cache and must release images it no longer shows (check the `drop_image` API in the pinned GPUI). Flags: `--page=library|store|settings`, `--section=general|personal|performance|other`, `--light`, `--no-focus`. Measured: window appears in ~0.3 s, ~90 MB on the settings page, ~142 MB with 30 thumbnails (release build, Windows).

## Gotchas found so far

- `Tab::icon()` makes an icon-only tab. Use `.prefix(icon)` together with `.label()`.
- `Select`'s outer container takes the full row width and collapses `flex_1` siblings (text renders one letter per line). Wrap it in a fixed-width `div`.
- Inside scroll containers give content a definite width when flex children must share space.
- Changing `Theme::global_mut(cx)` colors (`primary`, `slider_bar`, …) does not reach components that read semantic tokens (Switch, Slider). A real accent color needs a theme config, not direct color edits.
- `img(path)` decodes at full resolution and keeps it cached. For thumbnails decode yourself on a background thread at card size (`jpeg-decoder` DCT scaling, limited concurrency), build a `RenderImage` (BGRA), and pass `Arc<RenderImage>`. This took the prototype from ~230 MB to ~142 MB.
- Windows backdrops: `WindowBackgroundAppearance::{Blurred (acrylic), MicaBackdrop, MicaAltBackdrop, Opaque}`. gpui-pre-windows 0.3.12 `set_background_appearance` sets Opaque, Transparent and Blurred through SetWindowCompositionAttribute (the accent policy) and Mica/Mica Alt only through `DwmSetWindowAttribute(DWMWA_SYSTEMBACKDROP_TYPE)`, discards that HRESULT, and never clears one mechanism when it sets the other (so Acrylic stayed under Mica and a Mica type stayed under Acrylic, WR-14). The Portal therefore applies Opaque before any changed appearance (`theme::appearance_steps`; Window has no public getter, so the view remembers what it set), sets the DWM system backdrop type itself through `Platform::set_window_backdrop` (none for None and Acrylic, main window for Mica, tabbed window for Tabbed) and logs the OS answer as `dwm_result` on the "backdrop applied" line. A backdrop shows only while the Root fill is cleared (next bullet). gpui-pre-windows ignores Mica and Tabbed below build 22621 (Windows 11 22H2) and acrylic below 17763, so Sucrose reports the capability itself (`Capabilities.window_backdrop`, read with `RtlGetVersion`) and applies an unsupported stored backdrop as `Opaque`. The maintainer confirmed on the active Portal window on DISPLAY1 (03-47) that Mica, Tabbed, Acrylic and None each look different from None, in Dark and in Light, and that every switch between them in both directions changes the window (42 "backdrop applied" lines in that run, all `supported=true` and `dwm_result=0x00000000`), so the DWM frame needs no extension into the client area (before the Opaque reset they did not show, 03-43).
- Root surface: `gpui_kit::open_window` mounts `gpui_base::Root` around the app view, and gpui-component's `RootPlugin` (`WindowState::style`) paints `tokens.background` opaque over the whole window, under the view. A window backdrop shows only when the Root's own style background is transparent (Root refines its style after the plugin styles, so it wins). Set it through `window.root::<gpui_kit::base::Root>()` (`theme::apply_root_fill`), because `Root::update` panics in a window without a Base Root. Keep the theme tokens opaque (no `Theme::global_mut`): the switch thumb and other components paint `tokens.background`. For Backdrop None put the background back to None so the plugin fill shows again (GPUI clears an Opaque window to white). The Root exists only after `open_window`'s build closure returns, so a setting applied inside the view's constructor has to be deferred once with `cx.defer_in`. Plan 03-17's translucent page tint alone could not show the backdrop (G-03-5). Mica and Tabbed show DWM's fallback color on an inactive window.
- Theme: register a `ThemeConfig` file with `ThemeRegistry::load_themes_from_str`, put its themes into `Theme::light_theme`/`dark_theme` and switch with `Theme::change(mode, None, cx)`; never edit `Theme::global_mut(cx).colors`. `Theme::sync_system_appearance` follows the OS; `cx.observe_window_appearance` reports an OS light/dark change as an event (no polling).
- A background image is a full-window `img(Arc<RenderImage>)` inside an `overflow_hidden` absolute layer, placed with an explicit rectangle and `ObjectFit::Fill` (None, Uniform and UniformToFill need a rectangle the element cannot compute on its own). A multi-frame `RenderImage` animates by itself, so swap in its first frame while `Window::is_visible()` is false and release replaced images with `cx.drop_image(image, None)`.
- Opening a window from automation steals focus and can receive the user's keystrokes. Use `focus: false` (the prototype's `--no-focus`) for automated runs, and capture with `PrintWindow` instead of the screen. `PrintWindow` returns no content for an Acrylic window, so automated captures use Backdrop None; the exception is a real screen copy of the window's `DWMWA_EXTENDED_FRAME_BOUNDS` rectangle with the window raised topmost without activation (D-035 in `docs/DECISIONS.md`, used by plan 03-41), or the maintainer's eye.
- rust-i18n (Portal, D-20): `rust_i18n::i18n!("locales", fallback = "en")` at the crate root; every `locales/*.<lang>.yml` file loads as that locale (`legacy.en.yml` and `sucrose.en.yml` both merge into `en`), flat dotted keys resolve, and `t!` also takes a runtime `&str` key. A locale file with no entries (comments only) makes every lookup return the key, so never commit one. A key defined in two files of the same locale is ambiguous; `cargo xtask localize` leaves the reworded legacy keys out (`REPLACED_KEYS`) and a test checks the files share no key.

- `gpui_kit::assets::Assets` embeds only the default component icons; an icon such as `ImageOff` or `PackageX` renders as nothing until it is registered. The Portal's `assets.rs` composes `Assets` with `icon_assets!(PageIcons, [...])`; add the icons a page needs there (the full `AllAssets` catalog is not embedded).
- `RenderImage` takes BGRA with premultiplied alpha, so a thumbnail from the `image` crate (RGBA) needs the red/blue swap and a premultiply. Release every image through `atlas::release_image` / `atlas::release_images` (`apps/sucrose-portal/src/atlas.rs`), never with a direct `cx.drop_image(image, None)`: with no window, `App::drop_image` reaches only the windows in `App.windows`, and GPUI takes the window being updated (event handlers, render, observers of that window) out of that map for the update, so the drop silently misses it and the image keeps its atlas tile. The helper queues the drop with `cx.defer`, which runs after the outermost update when every window is back; GPUI tests in `atlas.rs` pin both the cause (a direct drop inside a window update leaves the entry) and the fix.
- `InputState` has no max length: `.validate(|text, _| text.chars().count() <= N)` refuses an edit that would pass it (a paste that is too long is refused whole), and `.clean_on_escape()` makes Escape clear the box. `InputState::set_value` emits no `Change`, so it is safe to call while rendering. The same validator can carry shared state (an `Rc<Cell<usize>>`) for a limit that follows the data, such as the digits of the last page number.
- A shortcut that must work wherever the focus is (Ctrl+F for the search box) goes through `cx.observe_keystrokes` on the root entity; an action bound on an element only fires while focus is inside it. Use `modifiers.secondary(cx)` for Ctrl on Windows and Linux and Cmd on macOS.
- `Empty` is `flex_1` and centers its content; for a block that starts 64 px below the top give it `.flex_none()` inside a column with a top padding. `EmptyHeader` is at most 24 rem wide, so a 24 px heading wraps; widen it with `.max_w()`. `gpui-component`'s `Pagination` has no jump field and no fixed slot scheme, so the legacy pagination bar is composed from `Button`s and an `Input`.
- `Skeleton::new()` defaults to full width and 16 px height; override with `.w()`, `.h()`, `.size_full()` and `.rounded()`.

- `App::open_url` and `App::write_to_clipboard` return nothing, so a failure cannot be observed. For the clipboard read the text back with `read_from_clipboard` and compare; for a link only log the attempt.
- Dialogs (`gpui_kit::component::WindowExt`): `window.open_dialog(cx, |dialog, window, cx| dialog.title(..).w(px(..)).child(..).footer(..))`; the builder can run again, so keep it cheap. A plain `Dialog` draws no buttons: compose a `DialogFooter` with a `Button` that calls `window.close_dialog(cx)`. Children go into a scroll container under the title and above the footer, and the surface is at most the viewport height minus 32 px; to keep another clearance give the body its own `max_h` and `overflow_y_scrollbar()` (`ScrollableElement`). `keyboard`, `overlay_closable` and `close_button` are fixed when the dialog opens, and anything that changes while it is open (a countdown) must live in an entity passed as `.footer(entity)` or `.child(entity)`.
- `Button` is a `ParentElement`: a clickable row with an icon and two lines of text is a ghost `Button` with children, which the keyboard reaches for free. `font_semibold()` and the other weights need `gpui_kit::component::StyledExt` in scope.
- `window.on_window_should_close(cx, f)` calls `f` from the platform, outside any entity update; reach the root entity through a `cx.weak_entity()` taken beforehand and `update` it. Returning false keeps the window open.

- Hover preview (library card): `.on_hover(|hovered, window, cx| …)` is a second listener next to `.hover(style)`, and an element takes only one `on_hover`. A multi-frame `RenderImage` in `img()` animates by itself only when three things hold: the img has an element id (`.id(("library-card-preview", index))`; the frame index is element state keyed by the global id, and `request_animation_frame` is only called when that id exists), the window is active, and `App::reduce_motion` is false (gpui-base reads the OS "Animation effects" switch at init; with it off the preview stays on frame 0). The preview is a child above the static thumbnail and costs nothing once it is removed; drop its frames with `atlas::release_image` (the pointer-leave handler runs inside the window's update, so a direct `cx.drop_image` would miss that window) when the hover ends or the page, search or setting changes, because `on_hover(false)` does not fire for a card that leaves the tree. A preview decode shares the thumbnail decode slots (`DecodeQueue::reserve`) and its result is checked against the state machine, so a result for a card the pointer left is released instead of shown. `observe_window_visibility` tells the view to stop when the window hides.

- Settings controls (Portal): a `Select` item can be disabled and still visible through `SelectItem::disabled`; override `SelectItem::render` to give the row an id and a tooltip that says why. `SelectState::set_selected_value`, `SliderState::set_value` and `InputState::set_value` emit no event, so they are safe for showing a broadcast value or reverting a rejected change. `SliderEvent::Change` fires continuously and `SliderEvent::Release` once at the end: send on Release, or after a short rest. `TabBar::on_click` takes `Fn(&usize, &mut Window, &mut App)`, so reach the owning entity through a handle taken beforehand and emit an `EventEmitter` event.

- Service link (Portal, D-033): no I/O runs on the GPUI thread. One thread reads the endpoint and one writes it; events reach the UI through an `async-channel` receiver awaited in `cx.spawn_in` (the task holds a weak handle to the view and ends when the view is gone), and the UI sends through a bounded sender to the writer thread. Connection state and the retry schedule are pure functions (`next_state`, backoff) tested without GPUI; only a connection that reached Welcome earns fresh retries.
- A crate-root `use gpui_kit::*;` also brings GPUI's `test` macro into scope. A test module that does `use super::*` then fails with "recursion limit reached while expanding #[test]"; import the names the tests need explicitly.
- Window activation: Windows refuses `SetForegroundWindow` from a process that is not the foreground one, so bringing an open Portal forward is two steps: the process the user just started (a second `sucrose` or Portal) calls `AllowSetForegroundWindow(pid)` for the open Portal, then the service sends `Focus`. The grant is sent even when it failed; the worst case is a flashing taskbar button.
- Hover previews did not animate in the release Portal (plan 03-24 finding): the preview `img()` had no element id, so GPUI kept no frame state and never requested animation frames (`img.rs`: `with_optional_element_state(global_id)`, `request_animation_frame` needs `global_id.is_some()`). Fixed in plan 03-28 by the id `("library-card-preview", index)`; the test `card_preview_paints_its_second_frame` (card.rs) renders a card in an active test window and proves the second frame is painted, `card_preview_without_an_id_stays_on_frame_zero` documents the cause. `hover_card` and `on_dwell` now log every early return (`hover preview not started`, field `reason`) and a started preview logs `preview playing` at debug level. The preview cost is still not in the UI-07 numbers until the D-25 runs are repeated.
- Memory while paging (UI-07, `MEASUREMENTS.md`): on the 500-theme library the Portal's working set kept rising across rounds (131 MB on the first page, 287 MB peak, 269 MB final) although the thumbnail cache is capped at 64 images / 48 MiB. The real 90-theme library stayed flat after round 1 (173 MB first page, 206 MB final). Leading cause found (plan 03-27): images released from inside a window update stayed in the sprite atlas (hover leave, page change, search, settings change and background change all run inside the Portal window's update, and `App::drop_image` with no window cannot reach that window). A leaked tile keeps its whole 1024 x 1024 BGRA atlas texture of 4 MiB alive, because gpui-pre-windows frees a texture only when its last tile is removed; a preview frame of 360 x 203 is about 0.3 MB, so about 100 hovers across 17 pages can pin tens of textures while thumbnails churn through the atlas. The control test `gpui_drop_image_during_a_window_update_misses_that_window` records the rule, and every release now goes through `atlas::release_image`. Result of the D-25 reruns (plans 03-37 and 03-38, release build, previews animating, rounds from the page log): the cause is confirmed for the 500-theme library, whose final working set is now 165 MB (134 MB on the first page, peak 188; private 156 against 125) and passes the rule that it failed before (269 MB), with the attribution 'within the cap' (private +31.3 MB: gpu atlas +20.0, held heap +10.0, retention +1.0, thumbnails +9.5 MB). The real library passes too (178 MB final against 143 on the first page), but its attribution reads 'unattributed' (private +57.4 MB at the round 3 end, gpu atlas +20.0 MB the largest part, about 27 MB unexplained) while its final value is back at +35 MB; this is recorded as found, no follow-up (F-1 to F-4) is selected because no scenario fails the rule. The caps stay as they are.
- Library grid scrolling (03-42, G-03-6, G-03-8): thumbnails are requested for the rows in view plus one row ahead, computed in `render` from the `ScrollHandle` offset and bounds and the fixed card height (`layout::rows_in_view`, `layout::cards_to_request`); an overflow-scroll div notifies its view on every wheel step and a scrollbar drag redraws the window, so no scroll listener is needed; the bounds are zero before the first paint, so the first request uses the window height. The bounds and the offset read in `render` are the previous frame's: GPUI clamps the offset to the content only in the scroll container's prepaint, after `render`, and neither that clamp nor a resize notifies the view, so after a content shrink (a wider window adds a column, a smaller margin or page size) or a taller window the cards in view stayed on the static `Idle` fill, which asks for no frame (WR-16). `grid::visible_rows` clamps the offset to the content height of the same rows (`layout::clamped_scroll_top`) and, through `Window::on_next_frame`, notifies the view once when the handle's bounds or offset differ from what `render` read (an exact comparison of the raw reads, so it stops after one extra frame). The cache never evicts a wanted thumbnail (`ThumbCache::insert_keeping`, `trim`) and the page reads it without reordering (`peek`); it holds more than 64 images / 48 MiB only while more cards than that are on screen and trims back when they scroll away. The earlier rule of 03-10 (queue only the first 64 cards of the page) left cards 65+ of a 100-card page as skeletons, and a thumbnail evicted while its card was off screen was never requested again. `overflow_y_scrollbar()` owns its own scroll handle, and `.vertical_scrollbar(&handle)` appends its overlay as a child of the element it is called on, which GPUI scrolls with the content (every child of a scroll container gets the scroll offset, absolute ones included), so on a scrolled element the bar moves away with the cards (WR-15). A view that sets the offset itself keeps `overflow_y_scroll().track_scroll(&handle)` on the scroll area and mounts `Scrollbar::new(&handle).axis(ScrollbarAxis::Vertical).viewport_from_layout()` in an `absolute().inset_0()` sibling inside a non-scrolling `relative()` wrapper, the shape of gpui-component's own `Scrollable` (`grid::scroll_area`). The bar follows `Theme.scrollbar_mode`, synced from the OS once at init: on Windows `Hover` while the OS auto-hides scrollbars (the default) and `Always` with "Always show scrollbars" on; a Portal started before the OS setting changed keeps the old mode. The maintainer confirmed on the desktop (03-47) that the bar becomes visible at the grid's right edge with the OS auto-hide setting, that with "Always show scrollbars" on it is on the right edge too, that wheel scrolling and dragging the thumb to the end of a 100-card page work in both modes and that the bar stays on the right edge while the cards move; after a window resize at the end of the page the cards in view kept their thumbnails without another wheel step (WR-16). A `Skeleton` animates forever and asks for frames even when scrolled out of view, so cards that are not loading get a static fill (`Thumb::Idle`).

## Patterns

- State lives in entities; long work runs on `cx.background_executor()`, results come back with `this.update(cx, …)`.
- Event plumbing: `cx.subscribe` / `cx.subscribe_in` for component state events (`InputEvent`, `SliderEvent`, `SelectEvent`), `cx.listener` for click handlers.
- Stop a child's click from reaching a clickable parent card: wrap it in a div with `.on_mouse_down(MouseButton::Left, |_, _, cx| cx.stop_propagation())`.
- gpui-kit has AccessKit roles and a layout direction (RTL) setting; neither is tested in Sucrose yet. Arabic and Hebrew are among the 25 languages, so verify RTL early.
- A dialog (`window.open_dialog`) focuses its own handle when it opens and the root returns the focus to the previous element when it closes, so nothing has to restore it. To focus a button of the dialog on open, give the button a caller-owned handle with `Button::track_focus` and call `window.focus(&handle, cx)` right after `open_dialog`. Escape and a click outside close a dialog by default; `on_ok`/`on_cancel` are not needed with a custom footer.
- A list of text boxes whose rows come and go (the arguments editor): keep the rows in a plain model, create an `InputState` pair per row with `default_value` and subscribe to `InputEvent::Change` with the row index; rebuild all pairs after a removal or a reset (indices shift) and push one pair for an added row, so typing never loses focus.
- PrintWindow captures cannot exceed the screen: Windows clamps the Portal window to the monitor height (about 1040 px here), also from `SetWindowPos` or a taller initial size. To see a control far down a long settings page in an automated capture, move its group to the top in a temporary local edit and revert it.
