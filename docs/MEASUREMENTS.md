**M1 video wallpaper, reading the numbers.** Same theme, same machine, same GPU (NVIDIA GeForce RTX 3050 Laptop GPU for both video renderers, shown by each process's own GPU Engine counters), one active monitor, 300 s average after a 60 s warm-up, measured one app at a time (`cargo xtask measure`; `--row` refuses two different adapters). The Rust renderer reached the RTX 3050 through the GpuPreference value its own service wrote (no manual entry; with `SUCROSE_LOG=debug` the renderer's "video GPU adapter" line (it creates a Direct3D device, so it is not logged at the default level) and the per-process counters name the same LUID 0x00000000_0x0000FAEB). RAM and CPU are at or below the C# MpvPlayer engine: the Rust service plus renderer use 301 MB working set against 596 MB for the three C# processes (505 MB for MpvPlayer + Backgroundog), 1038 MB private against 1215 MB, and 0.40 % CPU against 0.70 %. GPU 3D engine is level: 16.4 % for the Rust renderer against 16.1 % for C# MpvPlayer (R = 1.02, so the mpv options `deband=yes` and `profile=low-latency` stay for parity), with similar GPU memory (719 MB against 733 MB dedicated). The desktop compositor load is also level: dwm.exe 4.2 % (Rust run) against 4.8 % (C# run) on the Intel UHD that drives the internal panel. The first M1 rows (2026-11-22, plan 02-15) compared two GPUs: the Rust renderer ran on the integrated Intel UHD because the GPU preference was not ported yet, the C# MpvPlayer on the RTX 3050; they are replaced by the same-GPU rows above. "Private (commit)" is the sysinfo `virtual_memory()` value, which on Windows is PROCESS_MEMORY_COUNTERS_EX.PrivateUsage. The final M1 build (the row "final M1 build" of 2026-11-23) adds the checked placement read-back, the location watch and the re-place-all rule; in steady state it measured 299 MB working set, 1034 MB private, 0.43 % CPU and 16.4 % GPU against 301 MB, 1038 MB, 0.40 % and 16.4 % for the build of the first 2026-11-23 row, so RAM and GPU are level and CPU is 0.03 percentage points higher (0.43 % against 0.40 %, a difference inside the run-to-run spread of one 300 s sample; peak CPU 1.5 % against 1.1 %). The watch and the read-backs run only at a display change or when explorer moves its desktop window, and none happened during the sample. This row is Rust-only because the C# app was not re-measured: the machine rebooted since the 2026-11-23 C# run, so `--row` refuses to pair it with a renderer on a different LUID; the comparison with C# stays the first 2026-11-23 row.

**M2 Use between Video themes, reading the numbers.** Plan 03-11 asked whether LoadSource (the renderers keep running and load the new video) leaks memory compared with the restart the C# app does on every Use. It does not, on this machine and these two 4K videos: 30 Uses in 300 s left every renderer's private memory, working set and GPU dedicated memory at the level of the first Uses, the per-video medians moved by at most 5 MB, and the peak of each third of the run did not rise. After a load the renderer briefly holds the old and the new decoder state (about +100-160 MB private for a few seconds) and returns to its plateau; the plateau depends on the video (A about 1033 MB, B about 1098 MB private for renderer 0), not on the number of Uses. Two caveats: the run used two videos only (the test client alternates between the selected theme and the next playable one), and mpv's own caches are not visible per Use at this sampling rate; a library with many different large videos was not measured. The earlier hint of 756 MB working set after ten Uses came from an invalid first run (different builds and videos) and is not a measurement.

**M2 Portal library paging, reading the numbers.** UI-07 (decision D-25) asks that paging through the library for three rounds does not grow the Portal's memory: the final value must stay within the first-page value plus the 48 MiB thumbnail cache cap, and the end of round 3 must not be above the end of round 1 by more than 5 %. The maintainer paged forward and back through every page by hand in a release build while `cargo xtask measure --side portal` sampled the Portal process, once on the real library (90 themes, 3 pages) and once on the synthetic 500-theme library (17 pages). The real library passes on working set and private bytes (final 206 MB and 196 MB, round 3 end level with round 2). The synthetic library fails: the working set rose from 131 MB on the first page to about 221 MB by the end of round 1, stayed flat at 206-207 MB while the maintainer was idle on page 1, and rose again to 287 MB during rounds 2 and 3 (final 269 MB, private 262 MB), above both bounds. Two caveats apply: hover previews did not animate in either run (hover shows only the first frame), so the preview cache cost was not exercised, and the scenario 2 rounds did not match the fixed summary windows, so only the first page, peak and final values are used for the judgment. The failure is recorded here as found; the caps and the code were not changed in this plan, and both scenarios need to be repeated after the hover-preview defect is fixed.
